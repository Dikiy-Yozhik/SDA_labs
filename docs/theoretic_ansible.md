# Автоматизация развёртывания WeatherWise с помощью Ansible

В этом разделе описан предполагаемый способ выполнения требований уровней оценки 9 и 10. Из-за недоступности KVM внутри используемой среды WSL сценарий не был фактически выполнен на созданной KVM-виртуальной машине. Поэтому команды и ожидаемые результаты ниже представляют план проверки на совместимом Linux-хосте, а не отчёт об успешно проведённом запуске.

## Уровень оценки 9 — автоматизированное развёртывание

### Цель и схема решения

Для выполнения требований уровня 9 предполагается использовать Ansible для автоматического развёртывания WeatherWise на отдельной Linux-виртуальной машине. Приложение состоит из фронтенда и бэкенда, запускаемых с помощью Docker Compose.

Ansible должен подключаться к целевой машине, проверять наличие необходимых инструментов, устанавливать недостающие компоненты, доставлять файлы проекта и обеспечивать запуск контейнеров. Это позволяет хранить процедуру развёртывания в виде конфигурации, которую можно повторно использовать после изменения приложения или подготовки новой виртуальной машины.

Предполагается использовать две среды:

- **Управляющая среда** — Ubuntu в WSL, где установлены Ansible, исходные файлы проекта и playbook.
- **Управляемая машина** — Ubuntu Server в виртуальной машине, где установлены Docker и Docker Compose и работают контейнеры приложения.

Ansible подключается к управляемой машине по SSH. Устанавливать Ansible непосредственно на целевую VM не требуется. На ней должны быть доступны SSH-сервер, Python и инструменты, необходимые для запуска приложения. Подробнее: [Ansible Playbooks](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_intro.html) и [connection details](https://docs.ansible.com/projects/ansible/latest/user_guide/connection_details.html).

Схема развёртывания:

```text
контроллер (ubuntu в wsl)
  ├── исходники проекта
  ├── inventory.ini
  └── deploy.yml
          |
          | ssh
          v
ubuntu server vm
  ├── docker
  ├── docker compose
  └── /opt/weatherwise
        ├── frontend
        ├── backend
        └── compose.yaml
              |
              v
        контейнеры frontend и backend
```

Поскольку на используемых ноутбуках не удалось добиться доступности KVM внутри WSL, эта схема рассматривается как предполагаемый способ выполнения требований на совместимом Linux-хосте.

### Inventory: описание целевой машины

Для указания целевых машин Ansible использует inventory — файл со списком управляемых хостов и параметрами подключения. В проекте он располагается по пути `ansible/inventory.ini`.

Пример содержимого:

```ini
[weather_server]
weather-vm ansible_host=192.168.1.50 ansible_user=ubuntu

[weather_server:vars]
ansible_python_interpreter=/usr/bin/python3
```

Здесь:

- `weather_server` — группа управляемых машин;
- `weather-vm` — условное имя машины в inventory;
- `ansible_host` — IP-адрес виртуальной машины;
- `ansible_user` — имя пользователя Ubuntu, под которым Ansible подключается по SSH;
- `ansible_python_interpreter` — путь к Python на целевой машине.

Адрес `192.168.1.50` приведён только как пример. Перед реальным запуском его нужно заменить фактическим IP-адресом VM, доступным из управляющей среды. Пользователь должен существовать на целевой машине, а SSH-подключение должно быть настроено заранее. Предпочтительный способ аутентификации — SSH-ключ; пароли и приватные ключи не следует хранить в репозитории.

### Playbook: последовательность развёртывания

Основная процедура автоматизации описана в `ansible/deploy.yml`. Playbook задаёт последовательность задач, которые приводят целевую машину к требуемому состоянию.

В начале файла указываются целевая группа и основные переменные:

```yaml
---
- name: deploy weatherwise
  hosts: weather_server
  become: true

  vars:
    app_dir: /opt/weatherwise
    source_dir: "{{ playbook_dir }}/.."
```

Параметр `hosts` связывает playbook с группой из inventory. `become: true` позволяет выполнять задачи с повышенными привилегиями через `sudo`, что необходимо для установки системных пакетов, управления службой Docker и записи файлов в `/opt`. `app_dir` задаёт каталог приложения на VM, а `source_dir` указывает на корень репозитория на контроллере.

Playbook включает следующие этапы.

1. **Проверка и установка Docker и Docker Compose.** Сначала проверяются команды `docker --version` и `docker compose version`. Результаты регистрируются в переменных Ansible. Если инструмент отсутствует, выполняется установка соответствующего пакета средствами `apt`. Такой подход позволяет не выполнять установку повторно, если инструмент уже доступен. Этот вариант предполагает совместимую версию Ubuntu и доступность нужных пакетов в её репозиториях.

2. **Запуск Docker и включение автозапуска.** Модуль `ansible.builtin.service` задаёт `enabled: true` и `state: started`. Это означает, что служба должна запускаться после перезагрузки VM и работать в текущий момент.

3. **Подготовка каталога приложения.** Модуль `ansible.builtin.file` обеспечивает наличие каталога `/opt/weatherwise`. Если каталог уже существует, повторное выполнение задачи не должно менять состояние системы.

4. **Доставка файлов проекта.** Модуль `ansible.builtin.copy` передаёт на VM файл `compose.yaml`, каталог фронтенда и каталог бэкенда. Исходники берутся из репозитория на контроллере, а файлы назначения размещаются в `/opt/weatherwise`. При изменении исходников Ansible обновляет файлы на целевой машине.

5. **Сборка и запуск приложения.** Для управления контейнерами используется модуль `community.docker.docker_compose_v2`. Он управляет приложением через Docker Compose CLI и позволяет задавать желаемое состояние проекта. Для него необходимо установить коллекцию `community.docker` на контроллере и обеспечить наличие Docker Compose v2 на целевой машине. Документация: [community.docker.docker_compose_v2](https://docs.ansible.com/projects/ansible/latest/collections/community/docker/docker_compose_v2_module.html).

В предлагаемом playbook обработчик (`handler`) пересобирает и запускает приложение, если задачи копирования обнаруживают изменения. Затем отдельная задача обеспечивает наличие работающего Compose-проекта. Благодаря этому нет необходимости выполнять принудительную пересборку при каждом запуске, если файлы проекта не менялись.

Корректность этого сценария зависит от фактического состава репозитория и `compose.yaml`. Предполагается, что в корне проекта находятся `compose.yaml`, `frontend/` и `backend/`, а все необходимые для сборки файлы входят в эти каталоги. Если проект использует дополнительные файлы конфигурации, например `.env`, их доставку следует добавить отдельно.

### Подготовка управляющей среды и проверка подключения

В управляющей среде устанавливаются Ansible и SSH-клиент:

```bash
sudo apt update
```

```bash
sudo apt install -y ansible openssh-client
```

Затем устанавливается коллекция для управления Docker Compose:

```bash
ansible-galaxy collection install community.docker
```

После настройки SSH выполняется проверка подключения:

```bash
ansible -i ansible/inventory.ini weather_server -m ansible.builtin.ping
```

При успешном подключении ожидается `SUCCESS` с ответом `pong`. Этот модуль проверяет возможность войти на целевую машину и выполнить модуль Ansible с доступным Python. Это не обычный ICMP ping. См. [документацию ansible.builtin.ping](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/ping_module.html).

### Предполагаемая проверка развёртывания

После успешной проверки подключения playbook запускается командой:

```bash
ansible-playbook -i ansible/inventory.ini ansible/deploy.yml --ask-become-pass
```

Параметр `--ask-become-pass` позволяет интерактивно ввести пароль для повышения привилегий через `sudo`, если это требуется. Во время выполнения Ansible проверяет инструменты, устанавливает недостающие пакеты, подготавливает каталог приложения, доставляет файлы и запускает Docker Compose.

В конце запуска выводится сводка по целевым машинам. Для успешного выполнения ожидаются значения `unreachable=0` и `failed=0`. После этого проверяется состояние приложения на целевой машине:

```bash
sudo docker compose -f /opt/weatherwise/compose.yaml ps
```

Далее необходимо открыть опубликованный порт фронтенда с ноутбука и проверить, что страница загружается, а данные действительно поступают от бэкенда. Успешное завершение playbook само по себе недостаточно: необходимо также проверить работу приложения.

Для уровня оценки 9 требуется показать один успешный запуск playbook и работающее приложение. В данном случае это предполагаемый порядок проверки на совместимом Linux-хосте, поскольку на используемых ноутбуках KVM внутри WSL запустить не удалось.

## Уровень оценки 10 — идемпотентность playbook

### Что означает идемпотентность

Идемпотентность означает, что повторное выполнение одной и той же процедуры при неизменных исходных условиях приводит к тому же желаемому состоянию системы без ненужных изменений.

В этой лабораторной после первого развёртывания повторный запуск playbook не должен без причины переустанавливать Docker, пересоздавать каталоги или пересобирать образы. Фронтенд и бэкенд должны оставаться работающими.

Для этого playbook использует модули Ansible, ориентированные на состояние системы. Например, `ansible.builtin.file` обеспечивает наличие каталога, `ansible.builtin.copy` сравнивает исходные и целевые файлы, а `community.docker.docker_compose_v2` обеспечивает требуемое состояние Compose-проекта. Большинство таких модулей не вносят изменений, если желаемое состояние уже достигнуто, однако идемпотентность всего playbook зависит от его задач и параметров. Общие принципы описаны в [документации Ansible по playbook](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_intro.html).

В предлагаемой реализации обработчик пересборки срабатывает только тогда, когда задачи копирования обнаруживают изменения в файлах проекта. Если файлы не менялись, обработчик не должен запускаться, а заключительная задача проверяет и обеспечивает нужное состояние Compose-проекта.

### Предполагаемая проверка повторного запуска

После успешного первого развёртывания та же команда запускается повторно без ручного изменения состояния VM:

```bash
ansible-playbook -i ansible/inventory.ini ansible/deploy.yml --ask-become-pass
```

Ожидаемые условия успешной проверки:

1. Повторный запуск завершается без ошибок.
2. Ansible не переустанавливает инструменты, если они уже установлены.
3. Неизменившиеся файлы не отмечаются как изменённые.
4. Docker Compose сохраняет необходимое состояние сервисов.
5. Фронтенд и бэкенд продолжают работать после повторного запуска.

В идеальном случае второй запуск завершается с `changed=0`. Если `changed` больше нуля, нужно посмотреть, какие задачи Ansible отметил как изменённые, и определить, являются ли эти изменения необходимыми. Ненулевое значение `changed` само по себе не означает, что приложение сломано, но требует объяснения при проверке идемпотентности.

После второго запуска повторно проверяется состояние контейнеров:

```bash
sudo docker compose -f /opt/weatherwise/compose.yaml ps
```

Дополнительно проверяются открытие страницы с ноутбука и получение данных фронтендом от бэкенда. Это подтверждает не только успешное завершение автоматизации, но и сохранение работоспособности приложения.

### Соответствие требованиям уровней оценки 9 и 10

| Требование | Предполагаемый способ проверки |
|---|---|
| Ansible подключается к VM | Успешный запуск `ansible.builtin.ping` |
| Необходимые инструменты установлены | Задачи проверки и установки Docker и Compose |
| Файлы приложения доставлены | Проверка файлов в `/opt/weatherwise` |
| Compose запущен | Успешная задача Compose и проверка `docker compose ps` |
| Уровень оценки 9 | Первый успешный запуск playbook и работа приложения |
| Уровень оценки 10 | Успешный повторный запуск без ненужных изменений; сервисы продолжают работать |

Уровень оценки 9 предусматривает автоматическое развёртывание приложения на отдельной машине. Уровень оценки 10 дополнительно требует показать, что процедуру можно безопасно повторять.

**Ограничение проверки.** Из-за недоступности KVM внутри используемой среды WSL фактический запуск Ansible против созданной таким способом KVM-виртуальной машины не выполнялся. Поэтому inventory, playbook и последовательность команд представляют подготовленную процедуру для проверки на совместимом Linux-хосте. Для фактического подтверждения уровней 9–10 на таком хосте необходимо выполнить первый и повторный запуск, сохранить вывод Ansible и отдельно подтвердить работу приложения.
