# Диагностика недоступности KVM и предполагаемый порядок развёртывания

## 1. Проверенное оборудование и исходные условия

Перед выполнением лабораторной работы была предпринята попытка настроить **KVM внутри WSL 2** на двух компьютерах под управлением **Windows 10**. Целью было получить Linux-среду с доступом к аппаратной виртуализации, создать в ней виртуальную машину Ubuntu, а затем выполнить развёртывание приложения через **Docker Compose** и **Ansible**.

Проверка проводилась на следующих компьютерах:

| Параметр | Ноутбук 1 | Ноутбук 2 |
|---|---|---|
| Модель | Acer Extensa 215-32 | Lenovo ThinkPad E14 |
| Процессор | Intel Celeron N4500 | Intel Core i5-10210U |
| Операционная система | Windows 10 Pro | Windows 10 Pro |
| Архитектура процессора | x86-64 (64 бита) | x86-64 (64 бита) |
| Аппаратная виртуализация | Проверялась в настройках BIOS/UEFI и средствами Windows | Проверялась в настройках BIOS/UEFI и средствами Windows |

Таким образом, попытки выполнить работу не ограничивались одним компьютером. Проверка проводилась на двух ноутбуках с различными процессорами Intel. Аппаратная виртуализация рассматривалась как доступная на уровне оборудования и настроек прошивки; дальнейшая проблема возникала при попытке использовать **вложенную виртуализацию из WSL**.

Здесь важно различать два понятия:

- **Аппаратная виртуализация на хосте** — возможность процессора и прошивки поддерживать виртуализацию.
- **Вложенная виртуализация в WSL** — возможность передать необходимые аппаратные расширения из Windows и используемой среды WSL внутрь Linux-дистрибутива, чтобы он мог работать с KVM.

Даже если первое условие выполнено, это само по себе не гарантирует выполнение второго. Для данной лабораторной требовалось именно второе: запустить **KVM в Linux-среде WSL**, а затем создать в KVM отдельную **Linux VM**.

## 2. Проведённая диагностика и предпринятые попытки

Проблема не была обнаружена сразу после одной команды. Мы последовательно проверяли конфигурацию Windows, состояние WSL и наличие необходимых возможностей уже внутри Linux-дистрибутива.

### 2.1. Проверка виртуализации средствами Windows

В PowerShell использовалась следующая команда:

```powershell
get-ciminstance win32_processor | select-object name,virtualizationfirmwareenabled,vmmontormodeextensions,secondleveladdresstranslationextensions
```

Она позволяет проверить модель процессора и получить сведения о включённой в прошивке виртуализации, расширениях процессора для виртуализации и поддержке трансляции адресов второго уровня.

Эта проверка нужна для того, чтобы отделить проблему аппаратной конфигурации от проблемы программной среды. Полученные результаты нельзя автоматически трактовать как отсутствие поддержки виртуализации процессором: последующие действия были направлены на настройку WSL и передачу возможностей виртуализации внутрь Linux.

Дополнительно проверялись версия и состояние WSL средствами Windows:

```powershell
wsl --version
```

```powershell
wsl --status
```

```powershell
wsl -l -v
```

Эти команды позволяют установить используемую версию WSL, состояние подсистемы и версию WSL, в которой работают установленные дистрибутивы.

### 2.2. Проверка доступности виртуализации внутри Linux

После запуска Ubuntu в WSL проверялась архитектура Linux-среды:

```bash
uname -m
```

В результате была получена архитектура:

```text
x86_64
```

Это подтверждает, что Linux-дистрибутив работает в 64-битной среде x86-64. Однако сама по себе эта информация не подтверждает доступность KVM.

Затем проверялось, передаются ли внутрь Linux аппаратные расширения виртуализации Intel VT-x или AMD-V:

```bash
grep -m1 -oE '\b(vmx|svm)\b' /proc/cpuinfo
```

В проверенной среде команда не вывела признаков `vmx` или `svm`. Для нашего случая с процессорами Intel особенно важен флаг `vmx`.

Также проверялось существование устройства KVM:

```bash
ls -l /dev/kvm
```

Вместо информации об устройстве команда сообщила, что `/dev/kvm` отсутствует.

Наконец, при запуске WSL отображалось сообщение:

```text
wsl: Вложенная виртуализация не поддерживается на этом компьютере.
```

Это наиболее существенное наблюдение для данной работы. WSL явно сообщала о невозможности использовать вложенную виртуализацию, а внутри Linux отсутствовали признаки аппаратных расширений и устройство `/dev/kvm`, необходимые для предполагаемого сценария с KVM.

### 2.3. Попытки устранить ограничение

После обнаружения проблемы настройка не была сразу признана невозможной. Были предприняты дополнительные попытки добиться требуемого поведения WSL.

В частности:

- проверялись настройки виртуализации на компьютерах;
- изучалось состояние WSL и установленного Linux-дистрибутива;
- предпринимались попытки изменить используемую версию WSL;
- отдельно была предпринята попытка установить более старую версию WSL, загруженную из репозитория Microsoft на GitHub;
- после этой попытки проблема не исчезла: вложенная виртуализация по-прежнему не предоставлялась Linux-среде.

Таким образом, замена установленной версии WSL на более старую не привела к решению проблемы. При этом дальнейшая работа над лабораторной не должна основываться на предположении, что причина заключается в аппаратной неисправности или в недостаточной производительности ноутбука: собранные данные указывают на отдельную проблему передачи возможностей виртуализации в WSL.

## 3. Сопоставление результатов с известной проблемой WSL

В ходе диагностики была обнаружена проблема в официальном репозитории WSL на GitHub:

**[microsoft/WSL — Issue #40735: Nested virtualization unconditionally disabled on Windows 10 in lifted WSL](https://github.com/microsoft/WSL/issues/40735)**

В этом отчёте описывается ситуация, когда на компьютерах под управлением Windows 10 вложенная виртуализация не передаётся в WSL 2, даже если процессор поддерживает её, а в `.wslconfig` указано:

```ini
[wsl2]
nestedVirtualization=true
```

Согласно разбору автора issue, в современной, отдельно поставляемой версии WSL (так называемой **lifted WSL**, в том числе распространяемой через Microsoft Store или как сборка проекта с GitHub) присутствует проверка версии Windows. Для Windows ниже Windows 11 вложенная виртуализация отключается в коде конфигурации виртуальной машины WSL.

В отчёте указывается, что соответствующая ветка кода явно устанавливает `EnableNestedVirtualization = false` для Windows 10. В результате расширения виртуализации не передаются внутрь WSL, независимо от того, поддерживает ли их сам процессор. Автор issue также сообщает, что при таком поведении `/dev/kvm` отсутствует, а `vmx` не виден внутри дистрибутива. Эти симптомы совпадают с наблюдениями в ходе нашей диагностики.

> GitHub

Это важно для интерпретации результатов: наличие такой проблемы означает, что аппаратная виртуализация может быть доступна на уровне хоста, но при этом KVM внутри WSL всё равно окажется недоступен из-за ограничений программной реализации WSL для Windows 10.

Мы также пробовали сменить версию WSL, в том числе установить более старый вариант из GitHub, однако это не привело к успешному запуску KVM. Поэтому продолжение переустановок без изменения условий работы WSL не давало подтверждённого пути к решению.

**Вывод:** проверка проводилась на двух компьютерах, настройки виртуализации и состояние WSL исследовались, а смена версии WSL не помогла. Внутри Linux-среды не удалось получить доступ к необходимым для KVM аппаратным расширениям и устройству `/dev/kvm`. С учётом найденного отчёта о поведении WSL в Windows 10 наиболее вероятным препятствием является ограничение вложенной виртуализации со стороны используемой среды WSL, а не отсутствие поддержки виртуализации процессорами как таковой.

## 4. Предполагаемая настройка WSL и KVM в совместимой среде

Если бы вложенная виртуализация поддерживалась используемой версией WSL, следующим шагом была бы настройка WSL 2 и установка KVM с инструментами управления виртуальными машинами.

В Windows 11 для этого сначала проверили бы актуальность WSL и убедились, что Ubuntu работает именно в WSL 2:

```powershell
wsl --version
```

```powershell
wsl -l -v
```

Затем в файле `%UserProfile%\.wslconfig` указали бы:

```ini
[wsl2]
nestedVirtualization=true
```

После сохранения файла полностью перезапустили бы WSL:

```powershell
wsl --shutdown
```

Параметр `nestedVirtualization` предназначен для управления вложенной виртуализацией в WSL 2. Для применения изменений необходимо перезапустить среду WSL.

Внутри Ubuntu установили бы инструменты KVM и libvirt:

```bash
sudo apt update
```

```bash
sudo apt install -y qemu-kvm libvirt-daemon-system virtinst cpu-checker
```

Далее проверили бы доступность виртуализации:

```bash
sudo kvm-ok
```

```bash
ls -l /dev/kvm
```

```bash
virsh list --all
```

Если проверки прошли успешно, можно переходить к созданию VM. Если `/dev/kvm` отсутствует или KVM недоступен, следует вернуться к диагностике среды, а не пытаться устанавливать виртуальную машину поверх неработающего гипервизора.

Для создания и управления виртуальными машинами в Ubuntu используются QEMU/KVM и libvirt.

## 5. Предполагаемое создание Ubuntu Server VM

После успешной проверки KVM создали бы виртуальную машину с Ubuntu Server 24.04 LTS. Для лабораторной достаточно следующей конфигурации:

| Параметр | Значение |
|---|---|
| Имя VM | weatherwise-vm |
| Архитектура | x86-64 |
| Процессоры | 2 vCPU |
| Оперативная память | 3 ГБ |
| Диск | 25 ГБ |
| Сеть | NAT через сеть libvirt |
| ОС | Ubuntu Server 24.04 LTS |

Создание VM допускается выполнять вручную, поэтому можно воспользоваться графическим инструментом `virt-manager` или командой `virt-install`.

Пример команды на Linux-хосте с настроенным KVM, после скачивания установочного ISO:

```bash
sudo virt-install \
  --name weatherwise-vm \
  --memory 3072 \
  --vcpus 2 \
  --disk size=25 \
  --cdrom /path/to/ubuntu-24.04-live-server-amd64.iso \
  --os-variant ubuntu24.04 \
  --network network=default \
  --graphics spice
```

Вместо `/path/to/...` необходимо указать реальный путь к ISO. После создания VM завершили бы установку Ubuntu через консоль виртуальной машины и включили OpenSSH Server.

Затем проверили бы её состояние и IP-адрес:

```bash
sudo virsh list --all
```

Внутри VM:

```bash
ip -4 addr
```

Ожидаемый результат: работающая Ubuntu VM, доступная по SSH с управляющей машины. В случае WSL с NAT дополнительно потребовалось бы проверить сетевую доступность VM из Windows и WSL.

## 6. Как проверили бы работу приложения

На созданной VM установили бы Docker и Docker Compose, перенесли исходники проекта и файл `compose.yaml`, а затем выполнили:

```bash
docker compose up -d --build
```

Состояние сервисов проверили бы командой:

```bash
docker compose ps
```

После этого последовательно проверили бы:

1. **Запуск сервисов:** frontend и backend работают без ошибок.
2. **Доступность страницы:** браузер ноутбука открывает опубликованный порт фронтенда по адресу `http://<ip-адрес-vm>:<порт>`.
3. **Связь фронтенда с бэкендом:** в инструментах разработчика браузера, во вкладке Network, успешен запрос к API и на странице отображаются полученные от бэкенда данные.

Если страница не открывается, проверили бы публикацию порта в Compose, сетевой доступ к VM и правила брандмауэра. Если страница открывается, но данные не загружаются, проверили бы логи backend и настройки API-запроса фронтенда.

Такой порядок позволил бы продемонстрировать всю цепочку: **ноутбук → Linux VM в KVM → контейнеры Docker Compose → ответ backend, отображаемый во фронтенде.**
